frida检测对抗(libmsaoaidsec.so)

发表于2026-04-21|更新于2026-04-22|移动安全
|总字数:5.2k|阅读时长:24分钟|浏览量:

一、样本总体情况

  • 架构:AArch64,803个函数(451已命名),镜像大小0xA7A08

  • 自描述为”NagaLinker v8.83”(JNI_OnLoad中调用__android_log_write打印)

  • JNI_OnLoad(0x13A4C)本身只做转发,真正的反调试防护在.init_proc中由sub_1BEC4(位于0x1BEC4)触发,即so被dlopen时自动运行

  • 所有与Frida/调试相关的字符串均经过XOR加密,运行时在.bss(0x49000-0x490AB)就地解密,所以strings静态搜索完全无结果

  • 加密密钥分布在三张表:

    • qword_305D8 = 3字节周期{0x99, 0xA7, 0xEC}(sub_1B380使用,”libc.so”,”fork”)
    • qword_30670 = 3字节周期{0x99, 0xA7, 0xA9}(主检测循环sub_1C544/sub_1CEF8)
    • dword_305BC = 3字节周期{0x99, 0xA7, 0xA9}(TracerPid相关,sub_1AE48/sub_1AB54)

  • XOR算法:双层流程,偶数下标用key[4*(i%3)]一个字节,奇数下标用key_dword[i%3]低字节,循环两两处理

  • 绕过前（魔改版的frida，大场面前没有卵用）

  • 绕过后

三、检测函数与调用关系

3.1 启动链路

.init_proc (0x14400)

└─▶ sub_1BEC4 (0x1BEC4) [保存getpid==>dword_49014]

​ └─▶ sub_1B924 (0x1B924) [控制流平坦化的调度器]

​ ├─ sub_12D9C 机型白名单检查(Firefly-RK3399直接放行)

​ ├─ sub_1CEF8 libart.so::PrettyMethod hook检测

​ │ └─ sub_25B30 指令指纹比对 ==> 命中则sub_234E0(0)

​ ├─ sub_1B380 dlsym(“fork”) fork出子进程做PTRACE_ATTACH自我跟踪

​ ├─ pthread_create ==> sub_1B8D4 TracerPid轮询线程

​ ├─ pthread_create ==> sub_19E0C USB/ADB监控线程

​ └─ pthread_create ==> sub_1C544 Frida字符串/fd/maps扫描线程

3.3 shellcode细节(sub_234E0/sub_26334)

  • 密文位于

    ,解密后前8字节反编译为:

    d2800bc8 mov x8, #0x5E ; __NR_exit_group=94

    d4000001 svc #0

    d65f03c0 ret ; 永不到达

    d503201f nop ; ×4 填充

  • 参数a1作为x0传入,对应exit_group的退出码(通常传0,静默退出)

  • 这是典型的”裸syscall杀进程”手法,无论是否hook了exit/_exit/abort/kill都无效

3.4 自跟踪fork机制(sub_1B380)

  1. prctl(PR_SET_DUMPABLE,1)
  2. 在栈上构造0xF69F89FA8ECEF5和0xF29EC8FF,XOR解密得到”libc.so”和”fork”
  3. dlsym(handle, “fork”)取函数指针避开静态分析
  4. 调用fork,然后:
    • 父进程:pthread_create(…, sub_1AB2C, &child_pid),让子进程始终是ptrace本进程的tracer
    • 子进程:sub_1B144把cmdline尾部追加”:daemon”,调用Java android/os/Process.setArgV0和prctl(PR_SET_NAME,…)把进程名改掉,然后执行sub_1A0D8事件循环,不停对父进程做ptrace(PTRACE_CONT,…)
  5. 效果:外部Frida/gdb想ptrace(PTRACE_ATTACH,父pid,…)会因”Operation not permitted(已被跟踪)”而失败

3.6 Frida字符串扫描(sub_1C544,每4秒)

三个扫描并行:

  • sub_1BFAC:读每个/proc/self/task//comm,匹配gum-js-loop或gmain ==> _exit(0)
  • sub_1C158:readlink每个/proc/self/fd/,匹配linjector ==> _exit(0)
  • sub_1C26C:解析/proc/self/maps,过滤/data/local/tmp+权限含rx的段,dlopen并扫描导出表中的_AGENT_1.0和frida-agent ==> _exit(0)

3.7 ART Hook检测(sub_1CEF8)

按SDK选择正确的art::PrettyMethod符号==>dlsym==>sub_25B30对该函数指针指向的前若干字节做指纹比对(函数首指令被改写成B/LDR PC,[…]等跳转模式时命中) ==> sub_234E0(0)。

四、检测后的分支汇总

触发点 处理方式 对应特征
扫描到gum-js-loop/gmain/linjector/frida-agent _exit(0) 静默退出,返回码0(易误以为”正常结束”)
TracerPid异常或线程状态t/T sub_234E0(0) ==> exit_group syscall 绕过所有libc hook杀进程
ART PrettyMethod被hook 同上 同上
自跟踪fork失败 exit(1) 或 sub_11FA4 非零返回码
ADB打开且JNI异常 sub_11FA4 ==> exit_group 同上
一般ptrace错误 exit(1)(0x1A348) -

误导性返回码:检测到Frida特征时统一使用_exit(0),让调用方以为程序”正常结束”,这就是所谓的”静默死亡”,是比abort更隐蔽的反分析技巧。

五、未覆盖项说明

  • 未发现直接的端口连接检测(如connect 27042/27047),样本走的是进程名+库名+文件路径三位一体的识别
  • 未发现inotify、alarm、gettimeofday、clock_gettime时间差检测
  • 未发现直接对/proc/net/tcp的解析
  • 未发现对xposed/magisk/substrate的字符串,样本没有专门针对Xposed/Magisk的反制(但ART Hook检测会间接命中Xposed)
  • 未发现对/proc/self/exe和/proc/self/cmdline的完整路径校验(仅用cmdline做重命名)
  • 未发现LD_PRELOAD检测触发路径(虽然字符串”LD_PRELOAD”在0x2F57F但唯一xref0xCFEC处只是getenv查询,用于linker内部流程而非防护)

六、绕过建议

6.1 静态层面

  1. 改名/改路径:不要把frida-server落在/data/local/tmp,改为/data/data/<target>或其他目录
  2. 重命名Frida agent库:替换frida-agent.so里的”frida-agent”和”_AGENT_1.0”导出符号,以及Gum线程名中的gum-js-loop、GLibgmain

6.2 运行时hook对抗

  1. 线程名改名:在so加载后立刻对自身线程调用prctl(PR_SET_NAME,”xxxx”),替换gum-js-loop和gmain(Frida JS端可Process.setCurrentThreadName或直接prctl)
  2. fd链接隐藏:在注入完成后dup2并close原始fd,或把agent库从磁盘copy后memfd_create方式加载,让/proc/self/fd/*的readlink看不到linjector
  3. maps伪装:对落盘到/data/local/tmp的库改用memfd+dlopen_from_memory;或者hookfopen(“/proc/self/maps”)过滤掉r?xp且包含frida或/data/local/tmp的行
  4. hook/proc/%d/status:拦截fopen/fread/fgets,把TracerPid:字段改为0,把PPid:改回原始值
  5. hook/proc/%d/task/%s/stat:拦截同一对函数,把状态字段t/T改为R/S
  6. hookstrstr/strncmp:对”gum-js-loop”/“gmain”/“linjector”/“frida-agent”/“_AGENT_1.0”等字符串返回未找到
  7. 禁用定时线程:找到三个工作线程(其pthread_create回调为sub_1B8D4/sub_19E0C/sub_1C544),在pthread_create处直接return 0或将回调改为空函数

6.3 ptrace绕过

  1. 抢先attach:让自己的frida-server在目标so的.init_proc执行之前就已ptrace(PTRACE_ATTACH)目标进程(早于fork出守护子进程)
  2. hookdlsym:当查询key为fork时返回一个空包装,使sub_1B380的fork()返回-1,从而走sub_11FA4之前被提前阻断;或者让fork返回正值但不真正创建子进程

6.4 ART hook检测绕过

  1. 恢复Trampoline处函数首指令:在sub_25B30读取指纹前先把PrettyMethod前几字节恢复,读完后再下hook;可用Interceptor.replace+.revert()模式
  2. hook dlsym针对libart:对_ZN3art12PrettyMethod*这几个符号返回一个未被改动的影子函数地址

6.5 shellcode层面

  1. mmap拦截:hookmmap,当PROT_EXEC|PROT_WRITE|PROT_READ同时出现且size为0x1C时返回失败,阻断sub_234E0/sub_26334的shellcode执行
  2. SYS_exit_group拦截:使用seccomp或ptrace syscall hook,拦截x8==94的svc指令并忽略

6.6 整体思路

最稳妥的方式是:

  • 把上述检测函数在内存中的首地址(0x1B8D4/0x19E0C/0x1C544/0x1CEF8/0x1B380/0x11FA4/0x234E0)都patch为mov w0,0; ret(0x52800000 0xD65F03C0)
  • 或者在sub_1BEC4入口(0x1BEC4)直接ret,等效关闭整个防护
